## 1. 大小（占用，x86-64 gcc -O2 实测）

用 Python 解析 COFF/PE 节表（binutils `size` 在本机非白名单读不到明文）：

| 构建 | .text | .rdata/常量 | .bss(变量) |
|------|-------|-------------|-----------|
| scl.o（默认配置，消息开） | 10 048 B | 1 644 B | 896 B |
| scl_msg0.o（`SCL_CFG_MSG_EN=0`，消息裁掉） | 7 872 B | 412 B | 896 B |

- **RAM 运行态 ≈ 0.9 KB**（含 256B 脚本缓冲 + 8×32B 参数缓冲 + 变量 48B + 帧栈等），与设计估算 §5.4 一致；无 malloc。
- 消息关闭约再省 2.2 KB flash、1.2 KB 常量。
- 说明：x86 指令密度低于 MCU（ARM Cortex-M 通常更小）；具体以目标板 `arm-none-eabi-size` 为准。

## 2. 速度（命令分发吞吐）

脚本 `setret 1; while -b; setret 1; noop; while -e 5000`（5 次 × 10000 条业务命令）：

- **命令吞吐 ≈ 16 666 667 条/s**（-O2 x86-64 桌面）
- 平均每条业务命令 ≈ **1.5 个 SCL_Loop tick**（另有流程/空白子句开销）
- 说明：库每条子句推进一个动作（状态机），吞吐取决于主循环调用频率；MCU 上按需缩放。

## 3. 可靠性

- 结构错误不崩溃、结束后状态干净：缺引号 / 括号不配 / `if -t` 缺参 / `while` 缺 -b/-e / 纯分隔符 / 函数式后多余内容 / 参数超上限等 12 类用例全过。
- 超长脚本（>256B）被 `SCL_Run` 拒绝且保持空闲。
- **2000 次确定性随机模糊输入**（结构化 token 打乱 + 引号/括号/分隔符/关键字），每 100 次插正常脚本验证恢复性：全部不崩溃、可恢复、变量清零、回到空闲。
- 嵌套过深（>3）被拒；死循环由 `SCL_CFG_WHILE_MAX` 兜底（测试未触发但代码路径存在）。

## 4. 重复性

同一脚本（含 while/if/异步无）连跑 5 次：

- 输出**逐字节一致**；
- tick 数一致（ticks=28）；
- 内容正确（HIT×4）。

## 5. 复杂度（执行步数随规模）

- 子句数 N=20→21 tick、N=40→41 tick：**每子句 ≈1 tick + 常数**，近似线性 ✔
- 循环 `-e 400`→1203 tick、`-e 1600`→4803 tick：**随迭代次数线性** ✔
- `if` 段帧开销为小常数（if 分支+2 条 7 tick vs 平铺 3 条 4 tick）✔

## 6. 备注（测试中发现并固化的语义）

- `G_RETURN` "读后清零"：`while -e N` 做"上限循环"时，body 内每圈需重新置 `G_RETURN=true`（否则第二圈读到已清空的 false 提前退出）——这符合需求"每次读完重置"，已在 `doc/spec/scl-spec.md` 用示例说明，测试亦按此编写。
- 引号支持 `"`/`'` 交替嵌套，满足 `if`/`while` 嵌套时"分支里再写带引号 if"的需求。
